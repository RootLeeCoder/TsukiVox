TsukiVox · V0.75 语音搜索

语音搜索技术设计

用户按一次麦克风按钮，说出「找周杰伦的晴天」，头显直接给出 4 个可点播的视频候选。它不是语音输入法， 不把识别文字塞回搜索框；语音是一条独立的找歌入口，与 V0.7 已有的文字搜索并行存在。

状态 设计提案，尚未实现 版本 V0.75，V0.7 与 V0.8 之间的独立中间版本 基线 V0.7（头显内搜索点歌闭环已完成） 影响面 TsukiVox_Unity + TsukiVox_Server 撰写 2026-07-27 进度跟踪 voice-search-implementation.md

01用户看到的样子

茶几平板上的一次语音点歌，从按下到出结果

语音搜索复用 V0.7 已有的搜索结果页：同一块茶几平板、同样固定 4 行结果、同样的 + 点播按钮。 唯一新增的是页面顶部的录音区，它替换掉「输入框 + 搜索按钮」的位置，并保留一个切回键盘输入的入口。

交互约定

  • 一次点击开始，说完自动停。检测到静音约 800 ms 即提交，硬上限 6 秒；录音中再点一次为取消。已决定
  • 不用长按。Quest 控制器扳机长按配合射线抖动容易误放，点击-点击的状态更容易在头显里稳定命中。已决定
  • 录音时压低正在播放的视频音量（不暂停），避免把伴奏当成人声送去识别。已决定
  • 识别结果不自动点播第一首。翻唱、伴奏、现场版极易混淆，误点一次就会触发服务端下载任务；仍由用户点 + 确认。已决定
  • 开始与提交各给一次轻触觉反馈，复用 V0.7 麦克风触觉通道。待实测

与键盘输入的关系。需要把两件事分开：V0.7 的 QuestAndroidKeyboardInput 已经把系统键盘桥接到搜索框和服务地址框 （QuestConsumerUiPrototype.cs:1623，ROADMAP V0.7 章节），这是已完成的； 但真机实测显示该 Quest 上连系统浏览器和系统搜索框都无法输入中文， 所以「能弹出键盘」并不等于「能打出中文歌名」。

因此文字搜索的可靠输入目前是 BV 号与 ASCII，中文关键词输入不可依赖。 语音搜索不是为了修键盘——键盘桥接本身没坏——而是在头显里绕开中文 IME 这个外部限制， 直接用一句话表达点歌意图。两条入口并存：语音负责日常找歌，文字负责精确 BV 号查询。

02端到端管线

六步；Quest 只做采集与展示，识别与检索都在服务端

为什么不做流式识别

用户只说 3–6 秒，说完才有完整意图。Realtime/WebSocket 会带来连接恢复、会话状态和用量控制三类额外复杂度， 却不会让「说完到看到结果」这个时延显著变短——瓶颈在后面的 Bilibili 检索，不在识别。第一版用一次性 HTTP 短音频转写。 已决定

03系统分层与密钥边界

Quest 永不直连云厂商

服务端现状缺口：当前 TsukiVox_Server 的鉴权只是可选的共享 Bearer token （src/api.mjs 的 requireAuthorization），并且没有任何自身限流—— BILIBILI_RATE_LIMITED 是转发 Bilibili 的上游限流，不是本服务的配额。

语音接口会直接产生按时长计费的云端调用，因此它不能沿用这个现状：必须在同一版里加上按设备的并发与每日次数限制， 否则一个能拿到 origin 的调用方就能持续刷你的 ASR 账单。

04Quest 端音频采集

复用现有麦克风链路，不抢第二次权限

默认 Unity 后端已经在持续录制一个 48 kHz、2 秒长的循环 AudioClip （QuestAudioPrototype.cs:13-14，Microphone.Start(device, true, 2, 48000) 在 :234）。 现有电平计算已经在用 Microphone.GetPosition + GetData 读取尾部 512 个采样 （:719-729）。语音搜索按同一模式读取，只是窗口更大、并且持续累积到独立缓冲。

Native Oboe 后端目前拿不到 PCM。NativeOboeDryMonitor 只导出 Start/Stop/SetGain/SetMuted/GetStats/GetLastError，TsukiVoxNativeStats 里只有电平、 采样率、XRun 计数这类标量，没有任何原始缓冲出口。

因此第一版语音搜索只在默认 Unity 麦克风后端下可用；当用户启用了低延迟 Oboe 路径时， 要么临时切回 Unity 后端（会有一次重启麦克风的间隙），要么给原生插件补一个只读环形缓冲导出。 这是一个必须在实现前定下的分叉点。待决定

与返听链路的共存

  • 不停止麦克风、不重启 monitorSource：切换会在头显里听到明显的爆音或静音断点。
  • 录音期间把视频播放音量压到约 15%，结束后线性恢复；不要暂停视频，暂停会打断队列状态轮询的语义。
  • 识别期间保持返听正常工作，用户仍能听到自己的声音，这本身就是「系统在听」的反馈。

05状态机与失败可见性

每个状态都必须在平板上有对应文案

客户端目前读不到错误码。PlaylistClient 的错误解析只取 PlaylistErrorResponse{error} 这个自由文本字段，服务端已有的 BILIBILI_RATE_LIMITED、BODY_TOO_LARGE 等 code 并没有被结构化读出来。 语音搜索要做上面这套分类文案，就得先给客户端错误模型补上 code 字段。已决定纳入范围

06供应商选型

腾讯云主用，MiMo 备用；均可大陆部署

OpenAI、Azure、Google Chirp 全部排除：服务器计划部署在中国大陆境内，访问这些接口本身就是不稳定因素。 剩下两家都能在大陆直连，差别在于能不能把歌名和艺人名喂给识别器。

热词表怎么组装

服务端在每次识别请求前动态拼装，不使用控制台里的固定热词表：

// 128 词预算的分配
该设备最近 20 次点播的歌名与歌手   权重 10   // 用户自己的偏好最值得赌
该设备收藏列表                     权重 10
全局热门歌手 / 团名（含日英专名）   权重 8
易错同音歌名的正确写法             权重 11   // 谨慎，超级热词会影响整体字准

// 实际发送形态
HotwordList: "周杰伦|8,五月天|8,CRYCHIC|10,春日影|10,MyGO|10,晴天|8"

故障切换规则

  • 只在技术性失败时切换：连接超时、429、5xx。已决定
  • 不因为「识别结果看起来不对」而自动双调用。那会让成本翻倍，且结果不可解释——你无法回答「这个转写来自谁」。已决定
  • 服务端在内存里保留同一段音频，切换时直接转发，不重新向 Quest 索取。
  • 响应里带上 provider 字段供诊断抽屉显示，但不影响客户端逻辑。

MiMo 的音频隐私条款需要在正式发布前确认。其政策说明会收集 API 中的音频、境内数据存于中国大陆， 但没有给出音频的确切保留时长；「不用于模型训练」的表述明确覆盖的是文本内容，没有同样明确地覆盖音频。 作为故障备用可以接受，作为主通道则应先向小米书面确认。阻塞发布

07接口契约

一次请求完成识别 + 检索

语音搜索不能复用现有的 JSON 请求路径：src/api.mjs 里 jsonBodyLimitBytes = 128 * 1024，而一段 6 秒 16 kHz 单声道 WAV 约 192 KB，Base64 之后约 256 KB， 必然触发 BODY_TOO_LARGE。因此音频以裸 audio/wav body 上传，走独立的流式读取与独立上限。 已决定

请求

POST /api/voice-search
Content-Type: audio/wav
X-TsukiVox-Device-Id: 3f9a1c8e7b2d4a05...        // V0.7 已有的稳定设备 ID
X-TsukiVox-Audio-Ms: 4200                        // 端上实测时长，服务端仍需自行校验
Authorization: Bearer <token>                    // 若服务端配置了 TSUKIVOX_API_TOKEN

<binary WAV, 16 kHz mono 16-bit, ≤ 6 s, ≤ 512 KB>

成功响应

200 OK
{
  "transcript": "帮我找周杰伦的晴天",        // 原始转写，仅用于「听到：」回执
  "normalizedQuery": "周杰伦 晴天",           // 实际送去检索的词
  "intent": {
    "artist": "周杰伦",
    "song": "晴天",
    "modifiers": []                          // KTV / 伴奏 / 现场 / 原唱
  },
  "provider": "tencent",                     // 仅供诊断显示
  "audioMs": 4200,
  "page": 1,
  "pageSize": 4,
  "total": 42,
  "hasMore": true,
  "items": [ /* 与 /api/bilibili/search 完全相同的 BilibiliCatalogItem 结构 */ ]
}

items 刻意与现有 BilibiliSearchResponse 同构 （bvid, title, author, coverUrl, durationSeconds, durationText, viewCount, pageUrl）， 这样 Unity 侧可以直接把结果交给现有的 RefreshSongSearch() 渲染路径和 AddSearchResult() 点播路径， 不需要第二套结果模型。

08音频生命周期

录音只存在于内存，且尽可能短

  • Quest 端首次使用需要麦克风权限；V0.7 的返听功能已经申请过，因此通常不会出现新的权限弹窗。待实测
  • UI 上必须有明确的「正在录音」视觉状态（图 1 的电平条），不允许静默采集。
  • 设置页应提供语音搜索总开关，关闭后完全不采集、不上传。

09成本与配额

按次计费 vs 按时长计费

两家的计费口径不同，需要分别估。假设单次点歌语音 5 秒，一位活跃用户一晚 20 次：

必须随第一版一起落地的配额

  • 每设备并发 1：同一 X-TsukiVox-Device-Id 不允许并行语音请求。
  • 每设备每日次数上限：默认建议 200 次，环境变量可调。
  • 每分钟节流：远低于腾讯云 30 QPS 与 MiMo 100 RPM 的上限，防止端上 bug 导致连续提交。
  • 全局日预算熔断：达到阈值后返回 VOICE_QUOTA_EXCEEDED 而非继续付费调用。

11评测方法

指标是 Top-4 命中率，不是字准率

转写文本逐字一致并不重要，「用户想唱的那首歌有没有出现在 4 个候选里」才重要。 周杰伦 晴天 和 周杰伦的晴天 对最终检索结果没有区别； 而 春日影 被识别成 春日阴 就是彻底失败。

样本集（约 50 条，Quest 3 真机录音）

  • 普通话歌名 + 歌手：周杰伦 晴天、五月天 倔强
  • 日英专名与团名：CRYCHIC 春日影、MyGO!!!!!
  • 同音易错：蜜制 / 秘制 一类，验证热词权重效果
  • 带版本要求：晴天 KTV 伴奏、春日影 现场版
  • 中英混说与粤语各若干条
  • 口语包装：帮我找…、来一首…、我想唱…

每条样本在四种条件下各跑一次

  • 安静房间 / 视频仍在播放（有伴奏底噪）
  • 腾讯云（带热词）/ MiMo（无热词）

记录指标

  • Top-4 命中率（主指标）与 Top-1 命中率
  • 端到端时延：松手到结果出现，拆分为识别耗时与检索耗时
  • 单次成本与失败率（按错误码分类）
  • 热词开启 / 关闭的命中率差值——这一项直接决定腾讯云是否值得作为主通道

如果 MiMo 的 Top-4 命中率在无热词条件下已经追平腾讯云带热词的结果，主备顺序应当反过来—— 那样接入成本更低、按时长计费也更便宜。这个结论只能靠真机录音得出，不能凭文档判断。

明确不在 V0.75 范围

功能层面：

  • 哼唱识曲（听旋律找歌）——另一套技术栈，难度高得多
  • 连续对话与多轮追问
  • 语音控制播放（「下一首」「暂停」）
  • 识别后自动点播第一首
  • MiMo 通用 mimo-v2.5 音频理解直接抽意图——作为实验项评估，不作为生产回退路径

音频链路层面，这些属于 ROADMAP 的 V0.8「音频引擎打磨和安全」：

  • 任何对返听增益、动态处理、混响预设或滤波器参数的调整
  • Quest 扬声器反馈保护、削波与过热输入提示
  • 演唱音量校准流程

这条边界有一个实际后果：语音搜索只从现有麦克风链路旁路复制一份干声， 不修改音频处理。如果实现中发现必须改动返听链路才能取到干声，那是设计出了问题， 应当回到本文档重新讨论，而不是顺手调整音频参数。
